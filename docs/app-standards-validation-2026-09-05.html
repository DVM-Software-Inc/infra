01 / DECISION
Keep

The economical foundation

Docker Compose, Traefik, one VPS, product monorepos, shared application Postgres, a separate identity database, Keycloak realms per product/environment, BFF web authentication, native local-first defaults, and shared messaging.

These are sensible defaults for a solo developer. A shared host remains a shared failure and compromise domain.

Finish before launch

Identity and revenue controls

Prove complete app login/authorization, restrict identity administration at the proxy, cover Keycloak in scheduled recoverable backups, define audiences and native clients, finish ChatActorAI revenue gates, and prove its admin contract in a second SaaS.

Passing unit tests, a healthy container, and a planned feature are different kinds of evidence.

Invest for differentiation

Reliable, integrated AI

Use LLMs for domain extraction, grounded assistance, support drafts, and developer productivity. Reuse the metering/catalogue work. Evaluate actual customer tasks, meter every paid call, and make useful workflows survive a model outage.

No competitor benchmark was performed. These are testable differentiation hypotheses, not superiority claims.

Owner decision: disposable development identities. Authentik users, credentials, sessions, and other Authentik data do not need preserving or importing. Use fresh Keycloak accounts and reset/reseed affected dev identity references as needed. This audit did not delete data or decommission services. Ongoing status and acceptance evidence now live in the Keycloak migration control plane.

Customer-management adoption: applications that manage customers must use the ChatActorAI-derived SaaS administration standard described below and now canonicalized in saas.md. Product-managed AI uses the quality/cost control overlay in ai-product.md. Reuse common capabilities; enable billing, AI metering, and other modules only when the product needs them. The reference is still being finalized, so its unfinished controls remain explicit adoption gates.

What was actually validated

Evidence is deliberately scoped. “Observed” means checked during this audit; “documented” means reported by an existing runbook; “implemented” means present in inspected code, without a fresh end-to-end certification.

03 / FINDINGS

P0 · observedF01 · Product login hosts expose administration and unrelated realms

Finding: each observed product auth host returns the master admin UI, master discovery, and the other live product realm's discovery. The Compose routers match the whole host without path restriction.

Recommendation: path-scope each product HTTPS router to its own /realms/<product-env> tree plus required /resources/ assets. Put administration behind the separately restricted operator host/network; deny /admin, master, and unrelated realms at every customer entry point. Trust only proxy-supplied forwarded headers. KC_HOSTNAME_ADMIN alone does not block admin API access through other URLs.

Acceptance: master/admin/cross-realm probes are denied; product login, action email, reset, registration, broker callback, account UI, logout and assets still work; admin recovery works from the permitted path.

Evidence: live HTTPS probes; keycloak/deploy/docker-compose.yml:78; exact proposed router shape and shared verifier in the migration control plane. Keycloak hostname guidance and reverse-proxy guidance.

P0 · observedF02 · Keycloak is outside the inspected backup coverage

Finding: the backup container list does not include keycloak-postgresql. Its named volume also sits outside a simple archive of /opt/keycloak. Runbooks describing a service as “one tar away” do not provide a consistent live PostgreSQL backup.

Recommendation: include Keycloak DB, role definitions where needed, Terraform state, themes and provider extensions; encrypt off-host copies and protect recovery keys separately. Schedule the existing backup system and alert on missing runs. Adopt initial production targets of RPO ≤24 hours and RTO ≤4 hours, then adjust to business needs.

Acceptance: restore into isolation and prove fresh login, realm settings and application data access. A Terraform configuration replay does not restore users, credentials or sessions. No Authentik archival work is needed for this dev reset.

Evidence: db_back/.env:5; keycloak/deploy/docker-compose.yml:29; vps_deploy/infra_llm/docs/database.md. PostgreSQL consistent backup requirements.

P0 · updatedF03 · Public realm redirects work; complete the authenticated flows

Finding: the initial cc_dvm probe returned 404, but a later deployment/recheck returns 302 from its canonical login path to the exact product realm with state, nonce and S256 PKCE. gelopreto also reaches its exact realm with state and PKCE, but its inspected authorization/pre-auth/callback path does not create, persist, send or verify an OIDC nonce. The realm module now supports product-specific login, callback and logout paths.

Recommendation: retain the parameterized path contract; add and verify gelopreto’s nonce; record the remainder of each application flow in the migration ledger. Do not infer authorization, refresh/logout correctness, tenant isolation, or service-account correctness from the first redirect.

Acceptance: browser → product realm → callback → authorized app → refresh → logout succeeds through public routing, with wrong-state, wrong-nonce, wrong-realm/audience and wrong-role/tenant attempts rejected; gelopreto’s M2M path passes separately.

Evidence: 2026-09-05 public redirect/discovery/JWKS probes and gelopreto apps/web/lib/auth-oidc.ts; keycloak/docs/pilot-cc-dvm.md; keycloak/terraform/modules/product-realm; migration ledger and verifier.

P0 · standard repairedF04 · Adopt the complete token and authorization contract

Initial finding: base/fullstack guidance emphasized RS256 and JWKS but omitted a complete mandatory claims/authorization contract. The canonical base, fullstack, backend and iOS+backend prompts now define separate ID-token callback and API access-token rules, exact issuer/audience/time/subject checks, nonce and verified-email binding, local tenant/role/entitlement authorization, service/native clients, and rate-limited unknown-key refresh.

Remaining recommendation: implement and negative-test that contract in each migrated app. Declare API and messaging audiences/scopes explicitly in realm code; do not treat updated documentation as evidence that deployed validators comply.

Acceptance: validly signed wrong-realm, wrong-environment, wrong-audience/token-type, expired and unauthorized-tenant tokens all fail. Callback state/nonce and verified-email rules pass; signing-key rotation works without an extended outage or unbounded JWKS fetches.

Evidence: repaired base, fullstack, backend, and iOS+backend prompts; realm module and existing app implementations still require per-app conformance evidence. OAuth security BCP.

P0 · deployment controlF05 · SSH identity pinning is incomplete during deployment

Finding: the canonical workflow passes VPS_FINGERPRINT to the SSH action, but not to the SCP action that uploads Compose; the secret is optional. Production deployment also depends on caller environment restrictions, not just a manual button.

Recommendation: require a trusted host fingerprint and pass it to both transfer and execution steps. Verify it through an independent trusted path; unauthenticated ssh-keyscan alone is not identity verification. Restrict production source refs and minimize deploy-key permissions.

Acceptance: a wrong/missing fingerprint fails before any transfer; an unauthorized branch cannot deploy prod. Validate actual GitHub-plan environment features rather than assuming reviewer support.

Evidence: deploy.yml:70,157–184; environments.md. Existing action SHA pins are a positive control.

P0 · paid launchF06 · SaaS revenue safety needs observable acceptance

Finding: ChatActorAI has durable webhook ingestion, refund/dispute tests, reservations and plan/price models. Their presence does not prove a live payment, entitlement and AI-cost cycle is correct. Its production-readiness document explicitly leaves paid checkout behind a revenue gate.

Recommendation: require sandbox proofs for duplicate/out-of-order webhooks, annual monthly allowances, failed renewal, downgrade timing, partial refund, dispute hold, replay and concurrent credit use. Reconcile local payments/usage with processor records; cap and reserve every managed-model call. Launch prepaid/included allowances before postpaid overage.

Acceptance: an operator can trace charge → entitlement → consumption → refund/adjustment with no double benefit or unexplained balance. UI and marketing match enforced policy.

Evidence: ChatActorAI docs/12-production-readiness-plan.md, webhooks/stripe_router.py, metering/reservation.py, payment regression tests. Stripe webhook behavior; Billing test clocks.

P1 · repairedF07 · Keep agent instructions aligned with the canonical platform

Initial finding: .github/copilot-instructions.md mandated Dokploy, dokploy-network, :latest, restart: always, a dev branch and main→prod. It has now been replaced with concise routing to the canonical prompts, current deployment invariants, the SaaS overlay, and the Keycloak migration ledger.

Remaining recommendation: add a machine-readable standard manifest and deterministic drift check so obsolete networks, floating deploy tags, unsupported runtime defaults, and conflicting environment paths fail automatically. Generate copied agent context with its source revision/review date when cloud tooling needs vendored instructions.

Acceptance: the drift check rejects known obsolete patterns across advertised starters and active repos. LLMs may explain drift; deterministic checks decide pass/fail.

Evidence: repaired Copilot instructions; prompt routing; migration control plane.

P1 · partially repairedF08 · Finish runtime and starter consistency

Initial finding: prompts recommended EOL Node 20; backend-go built on unsupported Go 1.22 while another Go starter used a different line; final images ran as root or used a floating Alpine tag. The shared prompts/templates now default new Node work to Node 24 LTS, Go work to the current supported 1.27 line, Alpine 3.24, and non-root runtime users.

Remaining recommendation: lock application dependencies, pin validated release image digests, add a quarterly runtime review, complete or label placeholder framework starters, and replace sample CI placeholders with substantive checks and caller concurrency. Existing apps require compatibility-tested upgrades; this template change does not migrate them.

Acceptance: each advertised starter builds, starts as non-root where feasible, exposes a working healthcheck and runs substantive checks. Label incomplete starters as unsupported.

Evidence: repaired backend/fullstack guidance and Go/TypeScript templates. Node support lifecycle; Go releases/support policy; Alpine supported branches.

P1 · security precisionF09 · Social account linking depends on the flow, not one flag

Finding: module comments say trust_email=true automatically links an existing account. Upstream defines this flag as trusting provider email verification; account linking also depends on first-broker-login executions. The module relies on the stock flow rather than declaring its safety-critical behavior.

Recommendation: retain the currently tested conservative setting while explicitly configuring or asserting the broker flow. Test existing-account collisions with verified and unverified emails, confirmation-only bypass attempts, mailbox proof and existing-credential reauthentication. Do not optimize conversion by changing this flag alone.

Evidence: keycloak/terraform/modules/product-realm/main.tf:91 and pilot collision notes. Keycloak broker and Trust Email semantics. Prior collision success is documented, not rerun here.

P1 · native gapF10 · Native human login needs its own explicit standard

Finding: iOS+backend says mobile users receive app-issued tokens while human/admin surfaces use Keycloak. It does not define how a mobile human securely authenticates, refreshes or logs out.

Recommendation: for account-based native apps, use a public Keycloak client, system browser authentication, authorization code + S256 PKCE, registered redirect handling and OS credential storage. Never embed a client secret. Attestation is an abuse signal for anonymous access, not proof of human identity. Keep genuinely local apps account-free.

Evidence: ios-backend.md:40–49. OAuth for native apps.

P1 · web session gapF11 · BFF sessions, refresh and forward-auth are underspecified

Recommendation: standardize Secure, HttpOnly, host-only cookies, appropriate SameSite settings, CSRF/origin protection, state/nonce checks, session lifetime and revocation. Use a small opaque session identifier backed by Postgres/Redis when tokens or revocation needs exceed a sealed-cookie design. Test refresh races. Request offline_access only for a specific background-access requirement.

For protected static sites, Keycloak needs an OIDC-aware proxy/BFF integration; it does not replace Authentik’s outpost as a drop-in forward-auth endpoint. Scope OAuth2 Proxy sessions and clients by product, and still authorize API resources.

Evidence: frontend.md:22; fullstack.md:46–55. iron-session design; OAuth2 Proxy Keycloak integration.

P1 · shared-host riskF12 · Realm isolation does not constrain host resource use

Recommendation: set and load-test container memory/CPU budgets, JVM heap and DB pool sizes; alarm on saturation and restart loops. Consider a 2 GiB Keycloak container limit as a starting experiment, not a validated capacity figure; leave room for non-heap memory. Keep application DB access off the edge network when a planned network migration is practical.

One instance remains reasonable. Split dev/prod or move identity to a second host when availability or revenue justifies the extra operations; another container on the same VPS is not host-level resilience.

Evidence: live limits and memory snapshot; base.md:13–19. Keycloak container memory guidance.

P1 · database hardeningF13 · Database ownership is too much power for routine requests

Finding: app roles own their DBs; REVOKE CONNECT guidance is good, but does not make an owner unable to change schemas or disable protections. The older “short version” in the higher-precedence database runbook still omits isolation REVOKEs.

Recommendation: separate migration/owner and runtime roles; enforce tenant policy in API and DB for tenant data. Use FORCE RLS where appropriate and a runtime role without BYPASSRLS. Audit grants across existing DBs, connection limits and background-job tenant context. Remove the unsafe short provisioning example.

Evidence: base.md:183–218; vps_deploy/infra_llm/docs/database.md. Postgres RLS bypass/owner rules. Fresh PG15+ databases also changed public-schema defaults; inspect ACLs rather than asserting all versions grant PUBLIC CREATE.

P1 · release reliabilityF14 · A SHA-shaped tag is still mutable; deploy rollback is incomplete

Finding: rerunning a build for one commit can overwrite <env>-<shortsha>. A digest is available but deployments consume tags. Compose and .env are replaced before health success; no release snapshot/rollback transaction exists. Caller-wide cancellation can also interrupt a deploy despite the called job’s non-canceling group.

Recommendation: deploy digest-pinned service references; retain release metadata/config backups; test controlled rollback. Serialize mutation stages and use expand/contract schema changes. Promote the same artifact where config permits; if public config is baked per env, record and test the rebuilt prod digest.

Evidence: build.yml:93–118; deploy.yml:157–240; base.md:66–68.

P1 · cheap quality gateF15 · Local-first CI needs enforceable evidence

Finding: the no-PR-CI policy saves minutes but relies on a local gate that templates do not implement; reusable lint/tests just print a message. A passing placeholder can mislead both humans and agents.

Recommendation: keep macOS work local/on-demand and make a real scripts/check.sh mandatory. Capture the tested commit. Consider an explicitly approved policy revision for tiny Linux PR checks (auth contracts, secret scan, syntax); alternatively require the same checks on main before dev deployment. Never run untrusted CI on the production VPS.

Evidence: tests.yml, lint.yml, starter callers. Suggested PR checks are a policy change, not current convention.

P1 · SaaS reuseF16 · Prove the deployed ChatActorAI reference in a second SaaS

P1 · AI marginF19 · Make ChatActorAI’s AI controls cross-cutting

Register the contract

One product manifest: env, domain, realm, clients, callback paths, audiences, mail and role mapping.

Reset dev fixtures

Create fresh identities. Reseed affected app references and sandbox customer/billing fixtures. No Authentik import or archive.

Prove the app

Finish cc_dvm and gelopreto acceptance while smb-tax implementation proceeds; record positive and negative tests.

Retire old dependencies

Confirm every migrated service no longer requires Authentik. Remove obsolete clients/outposts/secrets and shut it down only after the fleet audit.

Repeatable migration acceptance

  • Fresh email signup, verification, reset and social collision paths succeed safely.
  • Exact callback routes, state, nonce and S256 PKCE checked through public ingress.
  • Customer, tenant admin and platform admin are distinct; an unassigned user cannot self-elevate.
  • Wrong product/env/audience tokens fail; tenant A cannot query tenant B.
  • Refresh, logout, revocation and signing-key rotation behave predictably.
  • Native or service-account path passes separately where present.
  • SaaS purchase/entitlement and Messaging subject registration use the new identity contract.
  • Application-specific old issuer/outpost dependencies are absent before retirement.

Operational contract for new identity data

Keep daily admin and break-glass access separate, with MFA, recovery material and an independent way to unlock the secret store. Alert on admin actions and login failure spikes without logging tokens or unnecessary personal data.

Protect Terraform state as a secret: local-file permissions are not encryption or off-host recovery. Use a reproducible pinned provider lock and a reviewed plan; validate destroy/recreate only on disposable probe realms. Add realm deletion protection before production identities exist.

Track migration status per app from an inventory, not a paragraph with a permanent “as of” date. A realm can be ready while its app is not.

The SaaS customer-management standard

Required overlay for products that manage customer accounts or customer relationships. ChatActorAI is the designated reference. Billing and AI modules are conditional; a simple free customer portal should not inherit a full metering engine.

Reuse a small package boundary

Finish the generic backend modules and UI primitives in ChatActorAI, then adopt them in one second SaaS. Publish a versioned dvm-platform-core and corresponding web components only once that second adopter proves the boundary.

Host apps supply identity, tenant context, DB/session interfaces, encryption and domain-specific dossier hooks. A shared library does not require one shared customer database or a new portfolio-wide microservice.

Retain one payment processor until a second has demonstrated business demand. Plan D’s conformance contract is useful; speculative PayPal code is not a launch prerequisite.

Make administration improve margins

One customer view should answer: what did they buy, what can they use, what did it cost to serve them, what is broken, and what action is safe now?

Show revenue, provider cost, credits reserved/used, failed payments, unresolved webhooks and support context. Give financial actions explicit amounts, currency, impact, idempotency and a reason.

LLMs may draft summaries and recommended replies over authorized records. A deterministic service authorizes and executes refunds, grants, plan changes and account actions after explicit operator confirmation.

Standards by application type and OS

Use the existing type standard plus applicable SaaS, messaging and AI overlays. Proposed extensions below are labeled; Android, Windows and Linux desktop do not yet have canonical org prompts.

06 / APP MATRIX
SaaS / browser / Linux host

Fullstack web application

Canonical: base + fullstack + backend + messaging. SaaS overlay required for customer management.

Existing: npm-workspace monorepo; apps/web Next.js/TypeScript, apps/api FastAPI, packages/*; separate images, ports 3000/8000; BFF over a private app network; shared Postgres and release-time Alembic migrations.

Improve: use a supported Node LTS; specify cookie/CSRF/refresh controls; expose the API publicly only for a defined consumer. Permit a simpler one-service TypeScript backend for small CRUD products through an explicit exception, instead of requiring two stacks for every app.

AI: domain extraction, cited document answers and workflow drafts through the metered server path. Customer panel uses the SaaS core.

Marketing / docs / browser

Public static site

Canonical: base + frontend. No customer-management overlay unless it actually manages customers.

Existing: one static nginx container, port 80, Traefik TLS; public build-time config only. SPA fallback where applicable. Next standalone port 3000 is also supported.

Improve: prefer generated static HTML for static content; set cache headers, compression, responsive assets and accessibility checks. Use immutable deploy references even though frontend.md still mentions moving env tags.

AI: offline drafts, translation and content QA with human review. Avoid adding runtime inference to a page that only needs to explain or sell a product.

Authenticated portal / browser

Frontend using an external API

Canonical: frontend; authentication design needs clarification.

Existing: no secrets in browser bundles. Add a BFF when server-held credentials are needed; product-specific identity realm.

Improve: choose BFF or explicitly configured OIDC proxy; proxy-login protection is not API authorization. If a public SPA OIDC client is justified, document the separate threat model and code+PKCE flow rather than silently violating the BFF standard.

SaaS/AI: reuse customer UI over authenticated APIs; LLM provider keys and paid-call controls stay server-side.

API / Linux container

Backend or integration service

Canonical: base + backend + messaging, when communication applies.

Existing: source /src; FastAPI 8000, Go 8080, Node 3000; /health and /api/v1; private workers; shared DB per app/env; separate migration step.

Improve: distinguish liveness from dependency readiness; add timeouts, payload limits, idempotency, API error contract and scoped machine clients. .NET/Django placeholder folders are not supported starter implementations.

AI: bounded background jobs with durable state and tenant budgets. Use deterministic parsers and calculations before inference.

Asynchronous worker / Linux

Jobs, ingestion and automation

Existing sidecar pattern; proposed explicit worker standard.

Existing: Redis/Celery workers and beat remain on app-private networks without public routes. Celery module registration is explicit in ChatActorAI.

Improve: idempotent job IDs, bounded concurrency, retry budget, dead letter, cancellation, queue-age alarms and transactional outbox. Start with a DB-backed queue when it meets needs; add Redis only for a measured requirement.

AI: batch embeddings, classification and enrichment; reserve cost before work and settle on completion. An agent never receives broad host or IdP admin authority.

iOS / iPadOS · local app

Native, account-free product

Canonical: ios + messaging; no VPS base needed.

Existing: Swift 6/SwiftUI, iOS 17+ baseline, phone/tablet families, XcodeGen, product bundle ID; shared logic in local SwiftPM kits; SwiftData local persistence and no CloudKit by default.

Improve: version/test local schema migration, export/restore, accessibility and device permissions. Define signing, TestFlight and release gates. Deployment target is a compatibility policy, not the SDK version used for submission.

AI: on-device classification or summarization when the OS/device/model supports it; deterministic fallback for older hardware. Cloud processing requires a product reason and informed data handling.

iOS / iPadOS + API

Account-based mobile SaaS

Canonical: base + ios + ios-backend + backend + messaging; SaaS overlay.

Existing: app + SwiftPM API kit + backend monorepo; xcconfig → project.yml → Info.plist; Debug/Staging/Release map to local/dev/prod. Scoped debug ATS exception only.

Improve: public Keycloak native client, system browser + PKCE, Keychain tokens and tested deep links. Unify staging hostname. Keep server APIs compatible with shipped versions; handle offline/retry conflict behavior. Evaluate store purchase rules per product/storefront.

SaaS/AI: consume the shared account/entitlement API; native support presentation over Messaging. Enforce paid AI budgets server-side, not in the app.

macOS · utility or desktop

Native Mac application

Canonical: macos + messaging; add server/web context only for those components.

Existing: SwiftPM-first core/app split; AppKit accessory app for menu-bar tools, SwiftUI for windows; macOS 13+ baseline; JSON non-secret config, Keychain secrets, permission fallbacks and local tests.

Improve: separate development signing from distribution. Specify Developer ID/notarization or App Store track, signed updates and rollback. A developer-owned provider secret cannot be safely shipped even if the app later stores it in Keychain; BYOK is a different model.

AI: on-device speech/text where suitable, optional metered cloud quality tier, cancellation and privacy-visible processing choices.

Android · proposed extension

Android application

No canonical org standard exists yet. Adopt only for demonstrated demand.

Proposed: choose native Kotlin/Compose if platform integration matters; otherwise evaluate a shared mobile stack against actual delivery cost. System-browser OIDC + PKCE, no client secret, platform key storage, separate release identity and permission controls.

Quality: emulator/device contract tests, signed release, store privacy/account deletion and purchase-rule review. Reuse backend SaaS/Messaging contracts rather than recreating them.

AI: capability-check local options; hosted inference through the same authorization and metering contract.

Windows / Linux desktop · proposed

Other desktop platforms

No canonical native Windows/Linux standard. Browser/PWA is the lowest additional-maintenance starting point.

Proposed: start with the web product unless offline, hardware or OS integration justifies packaging. Choose a native or webview shell after a concrete capability/security review; define signing, updates and OS credential storage.

Quality: keyboard/screen-reader support, installer/update verification and correct system-browser login. Do not export a desktop-specific framework choice into all products.

SaaS/AI: shared customer/entitlement and metered inference APIs; optional local model only after quality, memory and support-cost measurements.

The shared quality bar

One small inference contract

Begin as a library inside existing services: authenticated product/tenant context → deterministic policy → authorized retrieval → cost reservation → selected provider → schema/content validation → usage settlement.

Keep one evaluated default and one fallback/escalation option. Use provider/model identity, capabilities, effective prices and source timestamps from the SaaS catalogue. A fallback must satisfy the same privacy, residency, price and quality policy.

Cache exact reusable results with product/tenant/user permission scope, content revision and model/prompt version. Provider prefix caching can reduce input cost where supported; validate the selected provider’s current rules. Never share tenant-sensitive responses through a global cache.

Evaluation before expansion

Start with 50–100 representative, synthetic or consented cases plus adversarial cases; retain a held-out set. Include a deterministic baseline, cheap-model candidate and escalation candidate.

Proposed launch targets: ≥95% task correctness for a narrow low-risk extraction use case, zero observed cross-tenant leaks in the test suite, bounded p95 latency/cost, and no quality regression on upgrades. Targets vary by task; a small suite cannot prove zero future failures.

Use local versioned datasets and a lightweight test runner. Current OpenAI guidance says its hosted Evals platform is scheduled to become read-only October 31 and shut down November 30, 2026; avoid building a new dependency on it. Official evaluation guidance.

Keep authority outside the model. Retrieved pages, customer messages and model output are untrusted input. Deterministic code enforces identity, tenant access, money arithmetic, budgets and tool permissions. No autonomous account linking, role grants, refunds, production deployment or unrestricted SQL/shell. Human review is required for consequential proposed actions. OWASP LLM risks.

OpenAI’s Batch API documents a 50% discount for supported asynchronous workloads with a 24-hour completion window; use it for suitable noninteractive work, with expiry/retry handling. It is not a live-chat fallback. Batch documentation. Apple model availability must be checked at runtime. Foundation Models guidance.

Minimum SaaS release checklist

  • Registered type/OS + SaaS/Messaging/AI overlays and tested standard version.
  • Fresh Keycloak identity → correct local role and tenant → paid feature access.
  • Cross-tenant and operator-permission negative tests pass.
  • Renewal, cancellation, refund, replay and credit exhaustion work predictably.
  • Every business-funded model path has budget reservation and cost evidence.
  • Operator workflows are usable; customer-facing claims match shipped controls.
  • Health, external monitoring, backups, restore and deployment rollback have evidence.

What to postpone

Cross-product SSO, realm-per-customer design, a Kubernetes move, speculative microservices, multiple payment processors before demand, portfolio-wide GPU hosting, and autonomous financial/admin agents.

Keep framework/platform expansion tied to product demand. For new products, a complete tested reference is more valuable than many unfinished templates.

Adopt passkeys and lower-friction social signup after the account linking, recovery and compatibility tests are in place; measure completion and support burden.
