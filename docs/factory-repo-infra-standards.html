Overview

How the infrastructure standards library is organized and how it should be consumed.

What This Is

  • The sdlc-library/infra/ folder is the canonical set of infrastructure decision modules for the software factory. Each module is a versioned markdown file with front matter (category, option, version, priority, requires) plus normative sections (purpose, architecture rules, security requirements, do-not-deviate constraints).
  • Modules are composable: an application selects one infrastructure platform, one runtime, optionally one edge proxy, and one DNS/TLS strategy — or adopts a pre-composed stack preset that pins a known-good combination.
  • These standards apply across all DVM applications. Selecting a module means its rules, security requirements, and "DO NOT DEVIATE" constraints are binding for that application.

Module Anatomy

  • Cloud provider modules (infra_cloud_*, infra_vps_docker) use the full SDLC template: purpose, when-to-use, system role, tech stack definition, architecture rules, project structure, implementation standards, configuration, security, performance, observability, deployment, do-not-deviate, references.
  • Runtime / edge / DNS-TLS / environment modules use a lighter heading-based format covering provisioning, network layout, container runtime, config injection, storage, logging/metrics, and do-not-deviate constraints.
  • Stack presets declare explicit requires dependencies on other modules (e.g. Caddy requires the VPS Docker runtime), define required directories/files, runbook expectations, and standard env vars.

Alignment Gaps to Close (recommended updates)

1. Keycloak linkage — CLOSED 2026-09-18. Keycloak is the organizational identity standard: one realm per product per environment, with Google as an upstream identity provider of the product realm (per ~/code/infra/docs/standards.md and docs/keycloak-migration.md). The linkage is now explicit: auth_keycloak (v1.1) declares compatible_with all infra stack presets and infra_vps_docker; infra_vps_docker (v1.1) notes Keycloak deploys as a containerized service on this infrastructure; all three stack presets reference auth_keycloak. Apps composing infra modules now pick up the SSO standard automatically.
2. House default stack — CLOSED 2026-09-18. stack_vps_docker_traefik_letsencrypt (v1.1) now carries org_default: true in its front matter, declares compatibility with auth_keycloak and cicd_github_actions, and references the operational standard (~/code/infra/docs/standards.md) and Traefik templates (~/code/infra/docker-templates/traefik/). New applications adopt this preset unless a documented requirement selects another module.
3. Observability is vendor-framed but not tool-framed. Cloud modules name CloudWatch / Azure Monitor / Cloud Monitoring; VPS modules say "collect logs and metrics" without naming the org's chosen stack. Add a reference to the observability modules (sdlc-library/observability/) so the metrics/logging pipeline is chosen once, centrally.
4. Policy references are dangling for some modules. Cloud modules reference policy_secrets_management and policy_configuration; the runtime/edge modules reference "configuration policy" without a module ID. Unify on explicit policies/policy_* module references.
No blockers. Nothing found contradicts the standards in ~/code/infra/docs/standards.md. The factory library is a clean superset that the live infra repo already implements for VPS/Traefik workloads.

Cloud Providers

Three modules — select exactly one per application when using a public cloud platform. All are required priority v1.0

All three cloud modules share the same normative core: everything is provisioned through version-controlled Infrastructure as Code, environments are isolated (accounts / subscriptions / projects), least-privilege identity, resource tagging/labeling, private networking for workloads, managed secret stores, and audit logging. The differences are the provider-specific services.

AWS

sdlc-library/infra/infra_cloud_aws.md

  • IaC via Terraform, CloudFormation, or CDK; compute via ECS, EKS, Lambda, or EC2 (chosen by runtime modules).
  • Separate AWS accounts or explicit resource isolation per environment; VPC with explicit subnets, security groups, routing.
  • Public exposure only through load balancers or API gateways; private subnets for workloads.
  • Secrets via AWS Secrets Manager or Parameter Store; CloudTrail + GuardDuty for audit and threat detection.
  • Observability through CloudWatch or the org observability stack; blue-green or rolling deployments.
Do not deviate: no manual provisioning outside IaC; no * resource grants in production IAM policies.

Azure

sdlc-library/infra/infra_cloud_azure.md

  • IaC via Terraform, Bicep, or ARM templates; compute via App Service, AKS, Azure Functions, or VMs.
  • Separate resource groups or subscriptions per environment; VNET with explicit subnets, NSGs, routing.
  • Public exposure only through Application Gateway, Front Door, or load balancers.
  • Secrets and certificates in Azure Key Vault; Azure Monitor + Defender for Cloud for audit and threat detection.
  • Deployment slots, blue-green, or rolling deployments to minimize downtime.
Do not deviate: no manual provisioning outside IaC; no subscription-level Contributor RBAC for application identities.

Google Cloud

sdlc-library/infra/infra_cloud_gcp.md

  • IaC via Terraform or Deployment Manager; compute via Cloud Run, GKE, Cloud Functions, or Compute Engine.
  • Separate GCP projects per environment; VPC with explicit subnets, firewall rules, routing.
  • Public exposure only through load balancers or API gateways.
  • Secrets via Secret Manager; audit logging + Security Command Center for visibility.
  • Observability through Cloud Monitoring and Cloud Logging or the org observability stack.
Do not deviate: no manual provisioning outside IaC; no project-level Editor IAM bindings on service accounts in production.

VPS / Docker Infrastructure

Self-hosted model — the current operational default across DVM applications. required priority v1.0

VPS Docker

sdlc-library/infra/infra_vps_docker.md

  • Linux VPS hosts running containerized workloads with Docker Compose (or equivalent deterministic orchestration) and a reverse proxy for TLS termination.
  • Immutable images built in CI with deterministic version tags; containers run as non-root where feasible; health checks on all long-running services.
  • Only required public ports exposed through the reverse proxy; internal service traffic stays on isolated Docker networks.
  • Persistent database storage on managed volumes with documented backup procedures; environments separated by host or isolated deployment stack.
  • Project structure: deploy/ for compose definitions and deployment scripts, docker/ for Dockerfiles, .github/workflows/ for CI/CD.
  • Security: key-based SSH only, hardened firewall (required ports only), secrets kept outside committed compose files.
  • Declared compatible with backend_go, database_postgres, cicd_github_actions — a strong fit for Go API services and PostgreSQL on small-to-medium production footprints.
Do not deviate: no mutable application state in ephemeral containers without persistent storage planning; no production secrets in source-controlled compose files.

Runtimes

Three modules — select exactly one workload execution model per application. All are required priority v1.0

Kubernetes

sdlc-library/infra/runtime_kubernetes.md

  • Cluster bootstrap, namespaces, and baseline policies defined through infrastructure code — no manual console changes.
  • Public traffic enters via ingress/gateway resources; network policies restrict unnecessary east-west traffic.
  • Workloads declare explicit resource requests/limits, readiness and liveness probes, and use the correct primitive (Deployment, StatefulSet, Job, CronJob, DaemonSet).
  • Configuration injected via ConfigMaps, Secrets, mounted files; apps validate required config at startup.
  • Persistent data on PersistentVolumeClaims or managed external services; backup strategy aligned with the storage class.
  • Apps log to stdout/stderr; cluster monitoring covers pod health, restart loops, resource saturation, node capacity.
Do not deviate: no SSH-based host deployments or side-loaded processes that bypass cluster primitives.

Serverless

sdlc-library/infra/runtime_serverless.md

  • Managed functions, API gateways, queues, and data services provisioned through infrastructure code; no direct host management.
  • Workloads are short-lived, stateless functions with explicit memory, timeout, and concurrency settings per function.
  • No local filesystem treated as durable — durable state lives in managed databases, object storage, or queues.
  • Configuration via provider-managed env vars / secret stores, versioned through deployment automation and validated at init.
  • Provider-native structured logs, metrics, traces as baseline; alerting covers invocation errors, throttling, timeouts, downstream failures.
Do not deviate: no always-on hosts or long-lived sidecar assumptions on a serverless selection.

VPS Docker

sdlc-library/infra/runtime_vps_docker.md

  • Linux VPS instances with Docker Engine, Compose tooling, firewall rules, and OS patching automation; hosts managed, but app deployment always repeatable from code.
  • Only the edge proxy binds public ports; app containers, databases, and workers stay on private Docker networks.
  • Pinned image tags, health checks, restart policies, resource limits, explicit network definitions.
  • Config via env vars, mounted secret files, or a controlled secrets mechanism — never hard-coded production secrets in compose files; required vars validated at container startup.
  • Only approved state persists through named volumes or external managed storage; volume backups are part of the runbook.
  • stdout/stderr as log sinks; host monitoring covers CPU, memory, disk, and container restarts.
Do not deviate: no unmanaged host processes or parallel orchestrators bypassing container deployment standards.

Edge Proxies

Two modules — optional but exclusive; both require the VPS Docker runtime. optional priority v1.0

requires: infra_runtime / vps_docker

Caddy

sdlc-library/infra/edge_caddy.md

  • Routing in version-controlled Caddy config: explicit site blocks, hostnames, redirects, upstream mappings. Path rewrites kept minimal and documented.
  • Caddy terminates TLS and manages HTTPS redirects; internal services stay certificate-free on private container networks.
  • Upstreams point to named internal services — exposure is intentional, not inferred from running containers.
  • Security headers, forwarding behavior, request size limits, and proxy trust settings centralized in Caddy config.
  • Rate limiting via approved Caddy modules or application layer for tenant-aware controls.
Do not deviate: no parallel reverse proxy in the same ingress path.

Traefik

sdlc-library/infra/edge_traefik.md

  • Routes declared via labels or config files tied to containerized services; host/path rules explicit and version-controlled; catch-all routes fail closed.
  • Traefik terminates TLS at the edge; certificate config centralized, not duplicated in app containers.
  • Service discovery through Docker provider metadata; only approved services exposed — labels are part of the deployment contract.
  • Standard security headers, forwarded header handling, request size controls, HTTPS redirects at the edge; trusted proxy settings explicit.
  • Built-in middleware for basic rate limiting, request buffering, IP allow/deny.
Do not deviate: no second reverse proxy in front of or beside Traefik for the same traffic path.

DNS & TLS

Two modules — select exactly one certificate strategy. Both are required priority v1.0

Let's Encrypt

sdlc-library/infra/dns_tls_letsencrypt.md

  • Issuance and renewal automated by the edge layer or approved cert tooling; renewal monitored with alerts before expiry windows.
  • Public DNS carries A / AAAA / CNAME records to the edge endpoint; records stay consistent with the chosen HTTP-01 or DNS-01 challenge strategy.
  • Central domain management with predictable host naming (app, API, staging); wildcard certs require DNS validation and documented DNS-provider ownership.
  • Staging environment used for non-production issuance testing; production rate limits respected in automation and rollback.
Do not deviate: no manual certificate uploads or unmanaged renewal workflows on the same ingress path.

Managed TLS

sdlc-library/infra/dns_tls_managed.md

  • Issuance, renewal, and deployment handled by the cloud/platform provider; IaC references managed certificate resources explicitly and monitors their status.
  • Public DNS points hostnames to the provider-managed load balancer, API gateway, CDN, or ingress; validation records maintained through the approved DNS workflow.
  • Domain ownership, delegation boundaries, and subdomain conventions defined so certificate attachment and cutovers stay predictable.
  • Separate staging and production domains with independently issued certificates; non-production never relies on production bindings or hostnames.
Do not deviate: no manual renewal workflows layered on top of provider-managed issuance for the same endpoints.

Environments

One module — mandatory for every application. required priority v1.0

Dev / Stage / Prod

sdlc-library/infra/env_dev_stage_prod.md

  • Development, staging, and production are separate runtime environments with independent deployments, configuration, secrets, data stores, and integrations. Production data must never be written by non-production workloads.
  • Per-environment config values, endpoints, feature flags, and scaling settings, injected and version-controlled through deployment automation — never edited manually on running systems.
  • Secrets stored and rotated per environment; production secrets never reused in dev/staging; access controls narrow by environment.
  • Promotion follows dev → stage → prod through repeatable pipelines, preferring the same build artifact across environments with only configuration changes.
  • Schema changes and irreversible infrastructure changes require staging validation before production rollout.

Stack Presets

Three pre-composed, dependency-checked combinations — the fastest compliant way to start a new application. optional priority v1.0

VPS Docker + Traefik + Let's Encrypt house default

sdlc-library/infra/stack_vps_docker_traefik_letsencrypt.md

requires: infra_runtime / vps_docker · infra_edge / traefik · infra_dns_tls / letsencrypt
  • Default recommendation for small-to-medium deployments needing repeatable container hosting without cluster orchestration complexity. Matches the live ~/code/infra Traefik templates.
  • Requires version-controlled docker-compose.yml (or equivalent), edge proxy configuration/labels, environment/secret injection definitions, and deploy + rollback runbooks. Persistent services declare named volumes explicitly.
  • Runbooks must cover host provisioning, deploy/rollback, certificate renewal verification, log inspection, volume backups, and service recovery after host reboot; host patching and disk-capacity checks are mandatory operating tasks.
  • Standard env vars: APP_ENV, APP_PORT, PUBLIC_BASE_URL, LOG_LEVEL, DATABASE_URL, REDIS_URL, TLS_EMAIL. Production secrets never stored directly in compose files.
Do not deviate: no second ingress proxy or unmanaged certificate workflow in this preset.

VPS Docker + Caddy + Let's Encrypt

sdlc-library/infra/stack_vps_docker_caddy_letsencrypt.md

requires: infra_runtime / vps_docker · infra_edge / caddy · infra_dns_tls / letsencrypt
  • Default when a simpler file-driven edge configuration (Caddyfile) is preferred over label-driven discovery.
  • Requires version-controlled compose manifests, Caddyfile or equivalent edge config, environment/secret injection files, and runbooks for deploy, rollback, and certificate verification.
  • Runbooks cover host provisioning, deploy/rollback, Caddy config validation, certificate issuance verification, log inspection, and volume backups.
  • Same standard env var set (APP_ENV, APP_PORT, PUBLIC_BASE_URL, LOG_LEVEL, DATABASE_URL, REDIS_URL, TLS_EMAIL); secrets injected through approved mechanisms, not embedded in edge config.
Do not deviate: no second ingress proxy or unmanaged certificate path in this preset.

Kubernetes Ingress + Managed TLS

sdlc-library/infra/stack_kubernetes_ingress_managed_tls.md

requires: infra_runtime / kubernetes · infra_dns_tls / managed
  • Default recommendation for multi-service or higher-scale deployments needing cluster scheduling, declarative manifests, and managed certificate lifecycle.
  • Requires version-controlled manifests / Helm charts for namespaces, workloads, services, ingress, secrets references, and autoscaling; operational docs for cluster access, deployment, and rollback.
  • Runbooks cover manifest rollout/rollback, ingress validation, certificate provisioning checks, pod health triage, scaling issues, backup/restore, plus cluster upgrade and node-pool maintenance.
  • Env values come from ConfigMaps, Secrets, or external secret integrations (APP_ENV, APP_PORT, PUBLIC_BASE_URL, LOG_LEVEL, DATABASE_URL, REDIS_URL, cloud secret reference keys).
Do not deviate: no manual pod changes or unmanaged edge certificate workflows bypassing declarative cluster deployment.

Decision Guide

How to pick modules for a new application.

ScenarioRecommended Selection
Typical DVM service or web app (small-to-medium footprint) stack_vps_docker_traefik_letsencrypt (house default) + env_dev_stage_prod
Simple VPS app preferring file-driven edge config stack_vps_docker_caddy_letsencrypt + env_dev_stage_prod
Multi-service or higher-scale platform on a cloud provider infra_cloud_aws|azure|gcp + stack_kubernetes_ingress_managed_tls + env_dev_stage_prod
Event-driven / bursty workloads on a cloud provider infra_cloud_* + runtime_serverless + dns_tls_managed + env_dev_stage_prod

Composition Rules

  • Exactly one runtime module per application; the selected runtime's "do-not-deviate" constraints are binding.
  • Edge proxies (Caddy, Traefik) only apply under the VPS Docker runtime — they declare requires: infra_runtime / vps_docker and are mutually exclusive on the same ingress path.
  • Exactly one DNS/TLS strategy: Let's Encrypt for self-managed edge, Managed TLS for cloud/provider-managed ingress.
  • env_dev_stage_prod is always in force regardless of platform choice.
  • Prefer a stack preset over ad-hoc composition; presets carry the runbook and env-var contracts already wired together.
