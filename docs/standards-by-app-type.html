DVM Software — Infra Standards by App Type

One-page summary of conventions per application type.

Source of truth: ~/code/infra — docs/standards.md and prompts/ (base.md + one type file is the canonical LLM context). This page is a summary; when they conflict, the repo docs win.

🌐 Common (server apps) ⚡ Fullstack web 🎨 Frontend-only ⚙️ Backend-only 📱 iOS 📱⚙️ iOS + backend 🖥️ macOS ✉️ Messaging (cross-cutting)

🌐 Common — every server-deployed app base.md

Applies to fullstack, frontend-only, and backend-only apps. iOS/macOS-only apps skip this unless they gain a server component.

Topology

  • One VPS (Contabo, 194.238.24.254, ssh contabo) — everything is Docker Compose. No Kubernetes.
  • Traefik v3 owns 80/443, Let's Encrypt, discovers containers via labels on the external web-public overlay network. Never publish host ports; never bind 80/443/8080.
  • Shared Postgres 18 (pgvector/pgvector:pg18, container app-postgres): one DB + user per app+env, reached at postgres:5432. Not public; laptop access via SSH tunnel.
  • DB isolation is mandatory: REVOKE CONNECT ON DATABASE … FROM PUBLIC + REVOKE CREATE ON SCHEMA public FROM PUBLIC. One leaked DATABASE_URL = one database, never the instance.
  • Secrets only in Vaultwarden (vault.dvmsoftware.com) → GitHub secrets via bw get password … | gh secret set …. Never a value in repo, chat, or logs.

Environments, branching, domains

EnvDeployed byDeploy dirImage tagHosts
devpush to main (auto)/opt/apps/<slug>/dev:dev-<shortsha>dev.<domain> / api.dev.<domain>

  • No dev/prod branches — feature branches merge to main via PR. Each product owns its root domain (Namecheap); *.dvmsoftware.com is internal-only.
  • DNS A record → VPS must resolve before docker compose up, or Let's Encrypt HTTP-01 fails.
  • Monorepos are the default for products (repo named after the product); single-component repos are prefixed backend-go-*, frontend-nextjs-*, etc. Repo name = image name = deploy slug.

CI/CD contract

  • Reuse workflows from DVM-Software-Inc/infra (build.yml → deploy.yml) — never hand-roll scp/ssh deploys. Compose lives under deploy/ (enforced).
  • Immutable GHCR images ghcr.io/dvm-software-inc/<repo>:<env>-<shortsha>; never deploy a moving tag. Migrations run via migrate_command (pull → migrate → up -d).
  • secrets: inherit in callers (explicit secrets blocks resolve in caller context and break env secrets). VPS_FINGERPRINT must be the ECDSA host key fingerprint.
  • CI cost policy: no workflows on PRs/feature branches — local check.sh gates pre-merge; auto runs only on main and v* tags; macOS runners only in release workflows; every workflow carries the standard concurrency block.

Repo hygiene (required files)

  • Dockerfile per deployable service
  • deploy/docker-compose.yml — unique top-level name: <slug>-<env> (or --remove-orphans deletes other apps' containers!)
  • .env.example — variable names + Vaultwarden item refs, never values
  • .github/workflows/ci.yml calling the reusable workflows
  • docs/overview.md — hosts, services, env vars (what an agent can't infer)

Compose rules that bite

  • traefik.enable=true + traefik.docker.network=web-public; loadbalancer.server.port = container port; router names suffixed with env (unique VPS-wide).
  • Backing services (redis, workers) on an app-private internal bridge with no Traefik labels.
  • Monitored apps also join the external monitoring overlay (cc_dvm health + metrics) — declare it in compose; don't scaffold it away.
  • restart: unless-stopped (never always); no version: key; single-quote $ in .env; env_file: over interpolation for secrets.

  • One realm per product per env (<product>-dev|prod). No SSO between products — that's the feature. Email is the identifier; no global usernames.

  • Issuer is always the product's own auth host: https://auth.<product-domain>/realms/<product>-<env>. Finding key.dvmsoftware.com in app config = wrong.
  • Adding a realm = three coordinated changes: DNS A record, Traefik router (one per host), Terraform (~/code/keycloak/terraform/).
  • Google social login: one owner-approved master Google account; independent Cloud projects per product and environment. No new account per support mailbox, no mailbox-only IAM Owner grants. Support email may be visible.
  • Google’s exact redirect is the Keycloak broker endpoint: https://auth.<domain>/realms/<product>-<env>/broker/google/endpoint. Google OAuth secrets and Keycloak BFF secrets are different credentials, stored separately in Vaultwarden.
  • Dev OAuth stays in Testing; separate production projects require public branding/policy and applicable verification. An undeployed production website does not block dev login.

Product-host isolation, authorization/linking negative tests and refresh/logout remain open; working Google login is not full migration acceptance.
  • Acceptance includes state/nonce/S256 PKCE, exact issuer/audience, safe account linking, local tenant/role authorization and refresh/logout. Product auth hosts must deny admin, master and unrelated realms.

⚡ Fullstack web proven: chatactorai

React/Next frontend + FastAPI backend — the default pattern for any web-UI + API product. Also follows backend.md.

Repo shape — monorepo, npm workspaces

apps/api/ # FastAPI (Python, uv; source at apps/api/src/app/) apps/web/ # Next.js App Router (TypeScript) packages/* # shared TS packages (types, embeddable widgets…) deploy/docker-compose.yml docs/overview.md

Root package.json: "private": true, "workspaces": ["apps/web", "packages/*"]. No Turborepo unless genuinely needed.

Two containers, two hosts

ContainerStackPortProd host
webNext.js3000app.<domain>
apiFastAPI8000api.<domain>
  • Both join web-public (unique router names <slug>-<env>-web/api) and the app-private internal bridge.
  • Redis / Celery workers / beat sit on internal only — no Traefik labels. Postgres is always the shared VPS instance, never a compose service.
  • Images suffixed <repo>-api and <repo>-web.

Frontend build & serve

  • Next.js standalone output, multi-stage node:20-alpine, final CMD ["node", "server.js"], HOSTNAME=0.0.0.0 PORT=3000 (Traefik can't reach localhost binds).
  • NEXT_PUBLIC_* baked at image build time via ARGs → per-environment images. Never read them at runtime.

Auth — BFF pattern (the standard)

  • Next app is an OIDC backend-for-frontend against the product's Keycloak realm — openid-client + iron-session.
  • Browser holds only an encrypted session cookie; tokens never reach client JS.
  • Route handlers /auth/login|callback|logout + an /api/[...path] proxy attaching the bearer server-side, forwarding to http://api:8000 over internal.
  • FastAPI validates RS256 JWTs against the realm's JWKS (from OIDC_ISSUER_URL). Direct-to-API clients (widgets, integrations) use app-issued tokens/API keys.
  • Env vars: OIDC_ISSUER_URL, OIDC_CLIENT_ID/SECRET, OIDC_REDIRECT_URI, OIDC_SCOPES, SESSION_SECRET.

CI/CD deltas

  • Two build.yml calls (or a matrix) for -api / -web; the web build passes per-env NEXT_PUBLIC_* build args.
  • One deploy.yml; migrate_command runs Alembic (+ seeds) before up -d.
  • Test jobs first: ruff + pytest (postgres/redis service containers), next build, package builds.

🎨 Frontend-only frontend.md

A web UI with no backend of its own — the API it talks to is someone else's deployment (or there is none).

Shape

  • Next.js (default): standalone build per fullstack.md, container port 3000.
  • Pure static (Vite/React SPA, docs sites): multi-stage build ending in nginx:alpine serving /usr/share/nginx/html, container port 80.
  • Single container behind Traefik at app.<domain> (or the root domain).

Rules

  • Client config (NEXT_PUBLIC_* / VITE_*) baked at build time → per-env images.
  • Zero secrets in the container — anything in the bundle is public. If a secret seems needed, the app has a backend: switch to fullstack.
  • No auth in the SPA — front it with the product's Keycloak realm (forward-auth middleware, or a Next BFF). The SPA is a client of the realm; it never handles credentials.
  • SPA fallback for client-side routing: nginx try_files … /index.html.

⚙️ Backend-only backend.md

A single deployable API service behind Traefik at api.<domain> (or the root domain if no web UI). Source in /src.

Internal ports (container-side; Traefik label must match)

Dockerfile conventions

  • Slim multi-stage: python:3.12-slim (uv or pip), golang:1.2x → distroless/alpine, node:20-alpine.
  • Bind 0.0.0.0, EXPOSE the port, no secrets baked into images.

Required endpoints

  • GET /health → 200 JSON, no auth, no DB dependency if possible.
  • Public API versioned under /api/v1/….

Database & migrations

  • Shared VPS Postgres; Alembic via the deploy workflow's migrate_command (docker compose … run --rm api alembic upgrade head).
  • Never create_all() in production paths; never migrate on container start. Local dev may use SQLite or local compose Postgres via DATABASE_URL.

Auth

  • Machine/service clients: bearer tokens or app-issued API keys.
  • Human-facing endpoints (admin UIs, dashboards): OIDC against the product's Keycloak realm; issuer is the product's auth host, never key.dvmsoftware.com.

📱 iOS proven: health (ItHurtsDoctor)

No VPS footprint → base.md not required. messaging.md still applies if the app has user-to-business messaging.

Project setup

  • XcodeGen is the source of truth: .xcodeproj generated from ios/<AppName>/project.yml, never hand-edited, kept out of code review.
  • SwiftUI, Swift 6, iOS 17+, TARGETED_DEVICE_FAMILY: "1,2".
  • Bundle id com.<product>.app — product-branded, not com.dvmsoftware.
  • Shared/reusable logic (API clients, models, sanitizers) in local SwiftPM packages beside the app (ios/<KitName>/), zero external deps unless justified, with swift test coverage.

Build configurations = environments

  • Three configs in project.yml (Debug: debug, Staging: release, Release: release), one xcconfig each under Configs/.
  • Env values (server URLs, flags) live in xcconfigs → project.yml → Info.plist → read from Bundle.main. Never hardcoded in Swift. In xcconfig, write URLs as https:/$()/host so // isn't a comment.

Persistence & privacy defaults

  • Local-first SwiftData (@Model + ModelContainer, explicit Application Support store URL, cloudKitDatabase: .none unless sync is a product requirement).
  • No cloud storage of user data and no login by default; every NS*UsageDescription declared via project.yml.

CI (macos-latest, expensive)

  • workflow_dispatch only (plus v* tags once release exists) — never push/PR triggers. Pre-merge checks run locally: xcodegen generate + swift test + xcodebuild test.
  • Standard concurrency block; pin a simulator name with a fallback to any iPhone; coverage gathered in-scheme; tests required from day one.
Not yet standardized — do NOT invent: code signing, TestFlight/App Store release automation (fastlane vs Xcode Cloud), widget/watch targets. Surface the decision to the operator instead of picking a tool.

📱⚙️ iOS + backend proven: health

base.md + ios.md + backend.md apply; this defines the contract between app and backend.

Repo shape — one monorepo

ios/<AppName>/ # XcodeGen app project (per ios.md) ios/<KitName>/ # local SwiftPM package: APIClient + shared models backend_fastapi/ # FastAPI backend (backend.md; deployed per base.md) deploy/docker-compose.yml docs/overview.md

The API client never lives in the app target — it goes in the SwiftPM kit so it's unit-testable without a simulator.

Environment wiring (the core contract)

Backend base URL flows xcconfig → project.yml → Info.plist → runtime:

Build configBACKEND_BASE_URL
Debughttp://127.0.0.1:<port> (local backend)
Staginghttps://staging.api.<domain> (VPS dev)
Releasehttps://api.<domain> (VPS prod)
  • Runtime resolution: Info.plist → env-var override → compiled default (a small AppRuntimeConfig). Never scatter URL literals.
  • Debug localhost only via a scoped ATS exception — never disable ATS globally, never ship an exception in Release.

API contract

  • Versioned /api/v1/…; GET /health unauthenticated.
  • Mobile auth = app-issued tokens (or attestation-based anonymous tokens for privacy-first apps) — not session cookies. Human/admin surfaces use the Keycloak realm.
  • Sign in with Apple becomes mandatory once any other social login ships (App Store 4.8) — and it needs a generic OIDC provider + rotating client-secret JWTs. Plan before shipping Google sign-in.
  • Runtime credentials from build config or Keychain — never committed. Breaking API changes → new /api/v2 (old builds stay in the field).

CI

  • One workflow, parallel jobs: pytest (service containers), SwiftPM kit swift test, xcodebuild test on a simulator, then base.md build/deploy for the backend only.
  • iOS release automation: not yet standardized — ask, don't invent.

🖥️ macOS proven: talk2me

No VPS footprint. Add base.md + frontend.md if the repo ships a marketing site; base.md + backend.md if it gains a server. messaging.md always applies.

Repo shape — SwiftPM-first monorepo

Package.swift # swift-tools 5.9+, platforms .macOS(.v13)+ Sources/<Product>Core/ # portable library: ALL logic lives here, unit-tested Sources/<Product>/ # thin AppKit executable (the app) Sources/<Product>Smoke/ # optional CLI for exercising providers/APIs headless Tests/<Product>CoreTests/ ios/ # optional companion iOS app (XcodeGen per ios.md, # consuming the root package: packages: <Core>: path: ..) web/ # optional marketing site → frontend.md + base.md scripts/ # build-app.sh, check.sh, acceptance scripts docs/ # plans, specs, status/continuation notes
  • No .xcodeproj, no XcodeGen on macOS — SwiftPM is the project system (an Xcode project is added later only for archiving/notarization).
  • The core/app split is load-bearing: the app target stays a shell so logic is testable with swift test and reusable by the iOS app and CLI.

App conventions

  • Menu-bar/background utilities are AppKit accessory apps: LSUIElement=true in a hand-maintained Resources/Info.plist copied into the bundle. SwiftUI only for windowed apps and the iOS companion.
  • Bundle id com.<product>.app (legacy com.marcusc.* / com.dvmsoftware.* deviations — don't copy).
  • Every capability gets its NS*UsageDescription. Runtime-only grants (Accessibility) checked at use time with graceful fallback — never hard-fail on a missing permission.
  • Apple frameworks (Speech, AVFoundation, Foundation Models) + plain HTTPS over bundling third-party AI/audio libraries; zero external SwiftPM deps is the default posture.

Config & secrets

  • Runtime config: JSON at ~/Library/Application Support/<Product>/config.json (providers, models, endpoints).
  • Secrets only in the macOS Keychain — never in config, never in repo.
  • CLI/tests take <PRODUCT>_* env overrides (e.g. TALK2ME_PROVIDER, TALK2ME_API_KEY) for headless smoke tests.

Build, sign, verify

  • swift build -c release; scripts/build-app.sh assembles build/<Product>.app and codesigns down a documented chain: CODE_SIGN_IDENTITY env → Apple Development → Developer ID Application → local dev cert → ad-hoc. <PRODUCT>_REQUIRE_STABLE_SIGNING=1 forbids the ad-hoc fallback for builds that leave the machine.
  • scripts/check.sh (build + swift test) is the only per-commit gate — CI never runs on pushes or PRs.
  • CI: verify.yml dispatch-only on macos-latest (runs check.sh, no artifacts); release.yml dispatch + v* tags; non-Xcode jobs on ubuntu-latest.
Not yet standardized — do NOT invent: Developer ID notarization, DMG/zip packaging, Sparkle updates, App Store sandboxing/entitlements, signing team. Current state: local/dev distribution only.

✉️ Messaging — cross-cutting messaging.md

Required reading for every app type (web, iOS, macOS). Applies to authenticated user-to-business communication of any shape: chat, webmail, inquiry thread, message panel.

Required architecture

  • Integrate through the shared DVM Messaging API and its provider-neutral client/UI packages (source: ~/code/chatwoot repo).
  • Never call Chatwoot from a product backend or client — it's a replaceable engine behind the ChatwootAdapter. Never build an app-local messaging engine, message table, assignment queue, unread system, or polling loop.
  • Chatwoot IDs, inbox identifiers, API tokens, SDKs, and payloads are forbidden outside the platform's adapter/infra packages. Use platform-owned application/subject/conversation/message/context IDs.
  • ~/code/chatactorai is separate — the embeddable chatbot/RAG product, not the messaging system.
  • Peer-to-peer chat, game chat, and collaboration comments are out of scope — deliberate architecture decision required, don't force them into Chatwoot.

Integration contract

  • Each app registers once: stable application key, trusted auth/audience mapping, allowlist of messageable business-object types, per-object authorization, secure deep-link templates, owning team + escalation, notification policy + verified SES sender.
  • Context descriptors (e.g. {type: "inquiry", id: "inq_123"}) only after the platform can authorize the caller — a context ID, tenant ID, or email is never proof of access.

Identity & network

  • Web: BFF pattern — the BFF calls the Messaging API with the server-held token; browser JS never holds a provider credential.
  • Native: app-issued/Keycloak token contract; never bundle Chatwoot or notification-provider secrets.
  • VPS path: product containers join the external messaging-clients network and call the Messaging API by private alias (never chat.dvmsoftware.com or Traefik). Only the Messaging API/worker + Chatwoot Rails join messaging-backplane.

Notifications & config

  • Durable outbox + provider-neutral NotificationAdapter; apps never poll Chatwoot or reproduce unread counts/digests/retries. AWS SES for email; product code depends on neither provider directly.
  • Product config holds only provider-neutral values: MESSAGING_API_URL, MESSAGING_APPLICATION_KEY, MESSAGING_ENABLED. Keep integration off (false) until the shared service is deployed for the env — no accidental-permanent local backends.
  • Document a Messaging section in docs/overview.md (app key, context types, auth path, deep links, notifications).

Delivery gate (all 7 must pass before enabling)

  1. Unauthenticated access fails
  2. Cross-tenant / cross-application / guessed-context access fails
  3. No provider IDs or credentials in browser/native client
  4. Retries don't duplicate conversations, messages, or notifications
  5. Operator replies arrive via verified callbacks/webhooks, not polling
  6. Notification email uses the app's approved SES identity + deep link
  7. Operators see the app and business context in the central queue
